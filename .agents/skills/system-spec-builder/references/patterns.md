# Patterns — โครงสำเร็จรูปของระบบเล็กที่พบบ่อย

อ่านไฟล์นี้ก่อนเริ่มสัมภาษณ์ ถ้าไอเดียของผู้ใช้ตรงกับ pattern ใด ให้ **เสนอ** โครงนี้เป็นค่าเริ่มต้น แล้วถามแค่ว่า "ต่างจากนี้ตรงไหน" แทนการถามจากศูนย์

ทุก pattern ให้: ตาราง / ฟีเจอร์ MVP / สถานะ / ขั้นตอนหลัก / กติกาที่มักต้องมี (พร้อมที่บังคับ) / ที่มักพลาด (ถามให้ได้คำตอบก่อนเขียน)

ทุกตารางมี `id uuid` + `created_at timestamptz` อัตโนมัติ ไม่เขียนซ้ำด้านล่าง

เมื่อทำระบบประเภทใหม่เสร็จ ให้เพิ่ม pattern ลงท้ายไฟล์นี้

---

## P1. ระบบยืม–คืน (borrow/return)
คำที่บ่งบอก: ยืม, คืน, อุปกรณ์, หนังสือ, เครื่องมือ, ใครเอาไป

**ตาราง**
- `items` — name, code (รหัส, unique), category, quantity, available_qty, is_active, note
- `borrowers` — name, phone, department (ถ้าองค์กร)
- `loans` — item_id → items, borrower_id → borrowers, qty, borrowed_at, due_at, returned_at (null = ยังไม่คืน), note

**ฟีเจอร์ MVP**
- F1 จัดการรายการของ (เพิ่ม/แก้/ปิดใช้/ค้นหา)
- F2 บันทึกการยืม (เลือกของ + ผู้ยืม + จำนวน + กำหนดคืน) → `available_qty` ลด
- F3 บันทึกการคืน → returned_at, `available_qty` เพิ่ม
- F4 หน้ารวม: ของที่ถูกยืมอยู่ + ใครยืม + เกินกำหนดไหม

**สถานะ:** คำนวณจาก `returned_at` (null = กำลังยืม) และ `due_at < today` (เกินกำหนด) — ไม่ต้องมีคอลัมน์ status ใน loans

**ขั้นตอนหลัก:** เปิดแอป → เห็นรายการของ + คงเหลือ → กด "ยืม" → กรอกผู้ยืม/จำนวน/กำหนดคืน → บันทึก → คงเหลือลด → กด "คืน" → คงเหลือเพิ่ม

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| ยืมเกินคงเหลือไม่ได้ แม้กดพร้อมกัน | `CHECK (available_qty >= 0)` + function `borrow_item()` ลดยอดใน transaction เดียว |
| คืนเกินที่ยืมไม่ได้ / คืนซ้ำไม่ได้ | function `return_item()` ตรวจ `returned_at IS NULL` |
| รหัสของห้ามซ้ำ | `UNIQUE (code)` |
| ของที่มีประวัติยืม ลบไม่ได้ ให้ปิดใช้ | `is_active` + FK ไม่ cascade |

**ที่มักพลาด:** ของมีหลายชิ้นเหมือนกันไหม (ถ้าชิ้นเดียวทั้งหมด ตัด `qty` ออกได้) / ผู้ยืมต้องมีในระบบก่อนหรือพิมพ์สด / คืนบางส่วนได้ไหม (ถ้าได้ เพิ่ม `loans.returned_qty` และ `return_item(loan_id, qty)`) / ต้องมีกำหนดคืนทุกครั้งไหม / มีรายการของเดิมใน Excel ไหม (ปกติมี → นำเข้าใน Task ฐานข้อมูล) / แจ้งเตือนเกินกำหนด (ปกติเลื่อนไปรอบถัดไป)

## P2. ระบบจองคิว (queue booking)
คำที่บ่งบอก: จองคิว, รับบัตรคิว, เรียกคิว, นัดหมาย, ช่วงเวลา

**ตาราง**
- `services` — name, duration_min, is_active
- `slots` (เฉพาะจองตามเวลา) — service_id → services, date, start_time, capacity
- `bookings` — service_id → services, slot_id → slots (null ถ้าคิวเดินเข้า), customer_name, phone, queue_no, queue_date, status (`waiting`/`called`/`done`/`cancelled`), called_at (null จนกว่าจะถูกเรียก; เวลาจองใช้ `created_at`)

**ฟีเจอร์ MVP**
- F1 จัดการบริการ (เพิ่ม/แก้/ปิดใช้)
- F2 ลูกค้าจองคิว (เลือกบริการ [+ วัน/เวลา] + ชื่อ + เบอร์) → ได้เลขคิว + เห็นว่าอีกกี่คิว
- F3 หน้าเจ้าหน้าที่: คิววันนี้เรียงลำดับ + ปุ่ม เรียก / เสร็จ / ยกเลิก
- F4 จอแสดงคิว (กำลังเรียก + คิวถัดไป) สำหรับติดหน้าร้าน

**สถานะคิว:** waiting → called → done (→ cancelled ได้จาก waiting และ called)

**ขั้นตอนหลัก:** ลูกค้าเปิดลิงก์ → เลือกบริการ → กรอกชื่อ → ได้เลขคิว → เจ้าหน้าที่เห็นคิวใหม่ → กด "เรียก" → จอโชว์เลข → กด "เสร็จ"

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| เลขคิวไม่ซ้ำในวันเดียวกัน แม้กดพร้อมกัน | `UNIQUE (queue_date, queue_no)` + function `create_booking()` คำนวณ `queue_date` เป็นวันไทย, ล็อกด้วย `pg_advisory_xact_lock(hashtext(queue_date::text))`, แล้ว `max(queue_no)+1` และ insert ใน transaction เดียว |
| เปลี่ยนสถานะได้ตามแผนผังเท่านั้น และจดเวลาเมื่อถูกเรียก | function `set_booking_status()` ตรวจสถานะเดิม; ตั้ง `called_at = now()` เมื่อเข้า `called` |
| จองได้เฉพาะบริการที่เปิดอยู่ | API ตรวจ `is_active` ก่อนเรียก function |
| (ถ้ามี slots) จองเกิน capacity ไม่ได้ | function นับ bookings ต่อ slot ใน transaction เดียว |

**ที่มักพลาด:** จองล่วงหน้าตามเวลา หรือรับคิวหน้างาน (ตัดสินว่ามี `slots` ไหม) / มีกี่ช่องบริการพร้อมกัน / เลขคิวรีเซ็ตทุกวันไหม (ปกติ: ใช่, ใช้เวลา `Asia/Bangkok`) / เบอร์เดิมจองซ้ำในวันเดียวได้ไหม / คิวที่ถูกเรียกแล้วไม่มา ทำยังไง

## P3. ระบบลงทะเบียน / รับสมัคร (registration)
คำที่บ่งบอก: ลงทะเบียน, สมัคร, กิจกรรม, อบรม, ผู้เข้าร่วม, เช็คชื่อ

**ตาราง**
- `events` — name, date, location, capacity, registration_open (bool)
- `registrations` — event_id → events, name, phone, email, extra (jsonb สำหรับคำถามเพิ่ม), status (`registered`/`checked_in`/`cancelled`), checked_in_at (ว่างได้; เวลาสมัครใช้ `created_at`)

**ฟีเจอร์ MVP**
- F1 จัดการกิจกรรม (เพิ่ม/แก้/เปิด-ปิดรับสมัคร)
- F2 ฟอร์มลงทะเบียนสาธารณะ (1 ลิงก์ต่อกิจกรรม) → เต็มแล้วปิดอัตโนมัติ
- F3 รายชื่อผู้ลงทะเบียน + ค้นหา + ปุ่มเช็คชื่อ
- F4 ส่งออกรายชื่อเป็น CSV (server สร้างไฟล์ — เป็นการตัดสินใจระดับ ARCHITECTURE ข้อ 10 ต้องระบุใน SPEC 2.4)

**สถานะ:** registered → checked_in (→ cancelled ได้จาก registered)

**ขั้นตอนหลัก:** ผู้จัดสร้างกิจกรรม → ได้ลิงก์ → แชร์ → ผู้สมัครกรอก → ผู้จัดเห็นรายชื่อ → วันงานกดเช็คชื่อ

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| เกิน capacity ไม่ได้ แม้สมัครพร้อมกัน | function `register()` นับที่นั่งใน transaction เดียว |
| เบอร์เดิมสมัครซ้ำในกิจกรรมเดียวไม่ได้ | `UNIQUE (event_id, phone)` (ไม่นับที่ cancelled → partial index) |
| ปิดรับแล้วสมัครไม่ได้ | API ตรวจ `registration_open` |

**ที่มักพลาด:** ฟอร์มมีคำถามพิเศษอะไรบ้าง (ใส่ใน `extra`) / กิจกรรมเดียวหรือหลายกิจกรรมพร้อมกัน / ต้องยืนยันทางอีเมลไหม (ปกติ: รอบถัดไป) / ยกเลิกเองได้ไหม / กิจกรรมผ่านไปแล้วลิงก์ควรปิดเองไหม (ถ้าใช่ = งานตามเวลา ระบุวิธีใน SPEC 2.4)

## P4. ระบบคลัง / นับสต็อก (inventory)
คำที่บ่งบอก: สต็อก, คลัง, รับเข้า, เบิกออก, จำนวนคงเหลือ, ของใกล้หมด

**ตาราง**
- `products` — name, sku (unique), unit, min_qty, current_qty, is_active
- `movements` — product_id → products, type (`in`/`out`/`adjust`), qty, note, moved_at

**ฟีเจอร์ MVP**
- F1 จัดการสินค้า (เพิ่ม/แก้/ปิดใช้)
- F2 บันทึกรับเข้า / เบิกออก / ปรับยอด → `current_qty` เปลี่ยนตาม
- F3 หน้ารวม: คงเหลือทุกรายการ + ไฮไลต์ของต่ำกว่า `min_qty`
- F4 ประวัติการเคลื่อนไหวต่อสินค้า

**ขั้นตอนหลัก:** เปิดแอป → เห็นคงเหลือ → กด "เบิก" → ใส่จำนวน → คงเหลือลดทันที → ของใกล้หมดขึ้นสีแดง

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| `current_qty` ห้ามแก้ตรงๆ เปลี่ยนผ่าน movements เท่านั้น | function `record_movement()` เขียน movement + อัปเดตยอดใน transaction เดียว |
| เบิกเกินคงเหลือไม่ได้ แม้กดพร้อมกัน | `CHECK (current_qty >= 0)` |
| ลบ movement ไม่ได้ ให้บันทึก `adjust` แทน | API ไม่มี DELETE สำหรับ movements |

**ที่มักพลาด:** มีหลายคลังไหม (ถ้ามี เพิ่ม `locations` และ `current_qty` ต่อคลัง) / ต้องบันทึกราคาไหม / ใครเป็นคนเบิก (ถ้าต้องรู้ เพิ่ม `requested_by`) / ต้องมียอดยกมาตอนเริ่มระบบไหม

## P5. รายการทั่วไป (simple CRUD list)
ใช้เมื่อผู้ใช้ต้องการแค่ "เก็บรายการ ___ แล้วดู/ค้นหา/แก้ได้"
คำที่บ่งบอก: เก็บข้อมูล, ทะเบียน, รายชื่อ, บันทึก, ฐานข้อมูล ___ เล็กๆ

**ตาราง**
- `<records>` — ฟิลด์ตามที่ผู้ใช้บอก, is_active, updated_at

**ฟีเจอร์ MVP**
- F1 ดูรายการทั้งหมด + ค้นหา + เรียง
- F2 เพิ่มรายการ
- F3 แก้ไข / ปิดใช้
- F4 (ถ้าต้อง) กรองตามฟิลด์สำคัญ 1 ฟิลด์

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| ฟิลด์ที่ผู้ใช้บอกว่า "ห้ามซ้ำ" | `UNIQUE (...)` |
| ฟิลด์ที่เป็นตัวเลือกตายตัว | `CHECK (... IN (...))` + `shared/enums/` |

**ที่มักพลาด:** ฟิลด์อะไรบ้าง 5–8 ฟิลด์แรกที่สำคัญที่สุด / ฟิลด์ไหนใช้ค้นหาบ่อย / ฟิลด์ไหนห้ามซ้ำ / มีสถานะไหม / มีรายการเดิมต้องนำเข้าไหม

## P6. ใบแจ้ง / คำขอ / งานที่ต้องมีคนรับไปทำ (request / ticket)
คำที่บ่งบอก: แจ้งซ่อม, แจ้งปัญหา, ขออนุมัติ, ใบขอ, เบิก, ร้องเรียน, มอบหมาย, ติดตามสถานะ

**ตาราง**
- `requests` — ref_no (เลขที่ unique; ถ้ามีปีในเลขเช่น `R-2026-0001` ให้เริ่ม 0001 ใหม่ทุกปี), category (`CHECK` ตามที่ผู้ใช้กำหนด), title, description, location (ห้อง/แผนก/จุด), reporter_name, reporter_phone, status (`open`/`in_progress`/`done`/`rejected`), assigned_to (ว่างได้), resolved_at (ว่างได้), resolution_note (ว่างได้)
- `request_logs` — request_id → requests, from_status, to_status, note (ประวัติทุกครั้งที่เปลี่ยนสถานะ; เวลาใช้ `created_at`)

**ฟีเจอร์ MVP**
- F1 แจ้งเรื่องใหม่ (ฟอร์มสาธารณะหรือหน้าพนักงาน) → ได้เลขที่
- F2 หน้าผู้ดูแล: รายการเรื่องทั้งหมด กรองตามสถานะ/หมวด เรียงเก่าสุดก่อน + ปุ่ม รับเรื่อง / เสร็จ / ปฏิเสธ
- F3 หน้าดูเรื่องเดียว + ประวัติการเปลี่ยนสถานะ (ผู้แจ้งเปิดจากเลขที่ได้)
- F4 หน้ารวม: ค้างกี่เรื่อง แยกตามหมวด

**สถานะ:** open → in_progress → done (→ rejected ได้จาก open และ in_progress)

**ขั้นตอนหลัก:** ผู้แจ้งกรอกฟอร์ม → ได้เลขที่ → ผู้ดูแลเห็นเรื่องใหม่ → กด "รับเรื่อง" (in_progress) → ทำเสร็จกด "เสร็จ" ใส่บันทึก → ผู้แจ้งเปิดเลขที่แล้วเห็นว่าเสร็จ

**กติกาที่มักต้องมี**
| กติกา | บังคับที่ |
|---|---|
| เลขที่ไม่ซ้ำแม้แจ้งพร้อมกัน | `UNIQUE (ref_no)` + function `create_request()` ล็อกด้วย `pg_advisory_xact_lock` แล้วออกเลขถัดไปใน transaction เดียว (รูปแบบเลขระบุใน 1.7) |
| เปลี่ยนสถานะได้ตามแผนผัง และทุกครั้งต้องมี log | function `set_request_status()` ตรวจสถานะเดิม + insert `request_logs` + ตั้ง `resolved_at` เมื่อ done/rejected |
| หมวดต้องเป็นค่าในรายการ | `CHECK (category IN (...))` + `shared/enums/` |
| เรื่องที่ done/rejected แล้วแก้ข้อความไม่ได้ | API ปฏิเสธ PUT เมื่อสถานะปิดแล้ว |

**ที่มักพลาด:** ใครแจ้งได้ (ทุกคนผ่านลิงก์ หรือเฉพาะพนักงาน) / มีหมวดอะไรบ้าง (ขอรายการจริง) / ต้องแนบรูปไหม (ถ้าต้อง = อัปโหลดไฟล์ ระบุใน SPEC 2.4) / มีผู้รับผิดชอบหลายคนไหม (ถ้ามี `assigned_to` เป็นชื่อพิมพ์สด หรือตาราง `staff`) / ต้องแจ้งกลับผู้แจ้งไหม (ปกติรอบถัดไป ให้ผู้แจ้งเปิดดูเอง) / เรื่องเก่าที่ปิดแล้วต้องเห็นนานแค่ไหน
